# Chapter 10: Error Handling and Practical Projects

## Section 3: ES Modules and Code Organization

As your projects grow, one giant script becomes impossible to read, test or reuse. **ES modules** let you split code into small files that each do one job and share only what they choose. In Chapter 6 you learned the `import` and `export` syntax. In this topic you will use it to **organize real projects**.

---

## 1. Why Organize Code?

A single 1000-line file causes real problems:

* It is hard to find anything.
* Variable names clash with each other.
* Changing one part can break another.
* Teammates edit the same file and create conflicts.
* Nothing can be reused in a second project.

Splitting code into modules solves all of these.

* Each file has **one clear responsibility**.
* Each module has its **own private scope**.
* Only the things you `export` are visible to other files.
* Dependencies are written explicitly at the top with `import`.

---

## 2. Module Scope

Variables in a module are **private** by default. They do not become globals.

```javascript
// counter.js
let count = 0;                       // private to this file

export function increment() {
  count++;
  return count;
}

export function getCount() {
  return count;
}
```

```javascript
// main.js
import { increment, getCount } from "./counter.js";

increment();
increment();

console.log(getCount());
console.log(typeof count);    // count is not visible here
```

```output
2
undefined
```

Outside code can call `increment()` but cannot change `count` directly. This is called **encapsulation**.

---

## 3. Named Exports

A module can export many values by name. Importers must use the **same names**.

```javascript
// utils/math.js
export const PI = 3.14159;

export function add(a, b) {
  return a + b;
}

export function circleArea(radius) {
  return PI * radius * radius;
}
```

```javascript
// main.js
import { add, circleArea } from "./utils/math.js";

console.log(add(2, 3));
console.log(circleArea(10));
```

```output
5
314.159
```

You can also export at the bottom of the file, which gives you one clear list of what the module offers.

```javascript
// utils/text.js
function capitalize(word) {
  return word.charAt(0).toUpperCase() + word.slice(1);
}

function shorten(text, max) {
  return text.length > max ? text.slice(0, max) + "..." : text;
}

export { capitalize, shorten };
```

---

## 4. Default Exports

A module can have **one** default export. The importer can choose any name for it.

```javascript
// models/Task.js
export default class Task {
  constructor(text) {
    this.text = text;
    this.done = false;
  }

  toggle() {
    this.done = !this.done;
  }
}
```

```javascript
// main.js
import Task from "./models/Task.js";

const task = new Task("Learn modules");
task.toggle();

console.log(task);
```

```output
Task { text: 'Learn modules', done: true }
```

| Feature | Named export | Default export |
| --- | --- | --- |
| How many per file | Many | One |
| Import syntax | `import { name } from "./file.js"` | `import anyName from "./file.js"` |
| Name must match | Yes | No |
| Best for | Several helpers | The main thing a file provides |

Many teams prefer **named exports** because the names stay consistent and editors can auto-import them.

---

## 5. Renaming and Namespace Imports

Use `as` to rename an import and avoid a name clash. Use `* as` to gather everything into one object.

```javascript
// main.js
import { add as sum } from "./utils/math.js";
import * as MathUtils from "./utils/math.js";

console.log(sum(4, 6));
console.log(MathUtils.add(1, 1));
console.log(MathUtils.PI);
```

```output
10
2
3.14159
```

## 6. A Sensible Project Structure

Group files by **what they do**. A small web app might look like this:

```text
task-app/
├── index.html
├── css/
│   └── styles.css
└── js/
    ├── main.js            ← entry point, wires everything together
    ├── config.js          ← constants and settings
    ├── models/
    │   └── task.js        ← data rules (create, toggle, filter)
    ├── services/
    │   ├── storage.js     ← localStorage reading and writing
    │   └── api.js         ← fetch calls to a server
    ├── ui/
    │   └── render.js      ← DOM updates only
    └── utils/
        └── helpers.js     ← small reusable functions
```

A useful rule: **keep data, storage and display separate.**

| Layer | Responsibility | Touches the DOM? |
| --- | --- | --- |
| Models | Business rules and data shape | No |
| Services | Storage and network | No |
| UI | Drawing the page and reading input | Yes |
| Main | Connects the layers and handles events | Yes |

---

## 7. Putting It Together

Here is a tiny version of the layered structure. Each file does one job.

```javascript
// js/models/task.js
export function createTask(id, text) {
  return { id, text, done: false };
}

export function toggleTask(task) {
  return { ...task, done: !task.done };
}
```

```javascript
// js/services/storage.js
export function save(key, value) {
  return JSON.stringify(value);
}

export function load(text) {
  return JSON.parse(text);
}
```

```javascript
// js/main.js
import { createTask, toggleTask } from "./models/task.js";
import { save, load } from "./services/storage.js";

let task = createTask(1, "Write notes");
task = toggleTask(task);

const stored = save("task", task);
console.log(stored);
console.log(load(stored).done);
```

```output
{"id":1,"text":"Write notes","done":true}
true
```

Because `main.js` only **connects** the pieces, you can change how data is stored without touching the task rules.

## 8. Re-exports and Barrel Files

An **index file** can gather exports from several files, so other code needs only one import path.

```javascript
// utils/index.js
export { add, circleArea } from "./math.js";
export { capitalize, shorten } from "./text.js";
```

```javascript
// main.js
import { add, capitalize } from "./utils/index.js";

console.log(add(2, 2));
console.log(capitalize("codify"));
```

```output
4
Codify
```

Use barrel files for small, stable folders. In large projects, too many re-exports can slow down tools and hide where code comes from.

---

## 9. Modules Run Only Once

A module is executed the **first time** it is imported. Later imports reuse the same instance, so all files share the same data.

```javascript
// state.js
console.log("state.js is running");

export const state = { visits: 0 };
```

```javascript
// a.js
import { state } from "./state.js";
export function visitA() { state.visits++; }
```

```javascript
// main.js
import { state } from "./state.js";
import { visitA } from "./a.js";

visitA();
visitA();
console.log(state.visits);
```

```output
state.js is running
2
```

`state.js` printed its message only once, even though two files imported it.

## 10. Dynamic Imports

A normal `import` loads at the start. A **dynamic** `import()` loads a module **on demand** and returns a Promise. This keeps the first page load fast.

```javascript
// main.js
async function showChart() {
  const module = await import("./chart.js");
  module.drawChart("sales");
}

document.getElementById("showChartBtn").addEventListener("click", showChart);
```

* The `chart.js` file is downloaded only when the button is clicked.
* Use it for heavy features: charts, editors, maps and rarely used pages.
* Combine it with `try...catch` in case the file fails to load.

## 11. Using Modules in HTML

Add `type="module"` to the script tag. Press **Run** to see a module script in action.

```html
<!DOCTYPE html>
<html>
<body style="font-family: Arial, sans-serif; padding: 20px;">
  <h3 id="title">Loading...</h3>
  <button id="btn">Say Hello</button>
  <p id="output"></p>

  <script type="module">
    // In a real project these would be separate imported files.
    const config = { appName: "Codify Tasks" };

    function greet(name) {
      return "Hello, " + name + "!";
    }

    document.getElementById("title").textContent = config.appName;

    document.getElementById("btn").addEventListener("click", () => {
      document.getElementById("output").textContent = greet("learner");
    });
  </script>
</body>
</html>
```

In your own project, the same script would be `<script type="module" src="js/main.js"></script>`.

Facts about module scripts in the browser:

* They are **deferred** automatically, so the HTML is ready when they run.
* They always run in **strict mode**.
* They have their own scope, so top-level variables are not on `window`.
* Import paths must start with `./`, `../` or `/`, and must include the `.js` extension.
* Browsers load modules over **HTTP**. Opening the file with `file://` is blocked, so use a local server such as the VS Code **Live Server** extension.

## 12. Circular Dependencies

If file `a.js` imports `b.js` and `b.js` imports `a.js`, they depend on each other in a loop. This is a **circular dependency**. It can cause values to be `undefined` at the wrong moment.

```text
a.js  ──imports──▶  b.js
 ▲                    │
 └────────imports─────┘      ← avoid this loop
```

How to avoid them:

* Move the shared code into a **third file** that both can import.
* Keep the dependency direction one way: `main → ui → models`, never back.
* Pass values as function **arguments** instead of importing each other.

---

## 13. Guidelines for Good Organization

* One file, one responsibility.
* Name files after what they contain: `storage.js`, not `stuff.js`.
* Keep the entry file small; it should mostly import and connect.
* Put constants in one place, for example `config.js`.
* Keep functions that touch the DOM separate from pure logic.
* Prefer named exports for consistency.
* Do not export things that are only used inside the file.
* Keep the dependency direction simple and one-way.

## Real-World Example

A notes app whose logic, storage and display live in separate modules:

```javascript
// js/models/note.js
export function createNote(id, title) {
  return { id, title, pinned: false };
}

export function pinNote(note) {
  return { ...note, pinned: true };
}
```

```javascript
// js/ui/format.js
export function describe(note) {
  return `${note.pinned ? "[PINNED] " : ""}${note.title}`;
}
```

```javascript
// js/main.js
import { createNote, pinNote } from "./models/note.js";
import { describe } from "./ui/format.js";

const notes = [
  createNote(1, "Buy groceries"),
  pinNote(createNote(2, "Finish project"))
];

notes.forEach(note => console.log(describe(note)));
```

```output
Buy groceries
[PINNED] Finish project
```

## Common Mistakes

### Forgetting type="module"

```html
<script src="main.js"></script>                   <!-- import fails: SyntaxError -->
<script type="module" src="main.js"></script>     <!-- correct -->
```

### Leaving Out the File Extension

```javascript
import { add } from "./math";        // fails in the browser
import { add } from "./math.js";     // correct
```

### Using Curly Braces for a Default Import

```javascript
import { Task } from "./task.js";    // wrong if Task is the default export
import Task from "./task.js";        // correct
```

### Opening the Page with file://

Module imports are blocked on `file://` URLs. Use a local development server.

### Expecting Imported Variables to Be Assignable

```javascript
import { count } from "./counter.js";
count = 5;    // TypeError, imports are read-only
```

Export a function that changes the value instead.

### Creating Circular Imports

Move the shared code into a third module to break the loop.

### Putting Everything in One Giant Module

If a file does many unrelated jobs, split it by responsibility.

---

## Key Points

* Modules split a program into small files with private scope.
* `export` shares values; `import` uses them; the path must start with `./` or `../` and include `.js`.
* A file can have many **named** exports but only one **default** export.
* Use `as` to rename and `* as` to import everything under one name.
* A module runs only once, and every importer shares the same instance.
* Use `import()` to load code on demand.
* In HTML, use `<script type="module">` and serve files over HTTP.
* Separate models, services, UI and the entry file.
* Avoid circular dependencies by extracting shared code.
* Imported bindings are read-only.
