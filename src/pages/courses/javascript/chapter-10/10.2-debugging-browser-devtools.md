# Chapter 10: Error Handling and Practical Projects

## Section 2: Debugging with Browser DevTools

Every developer writes bugs. What separates beginners from professionals is how quickly they **find and fix** them. Browser DevTools is a built-in toolbox that lets you inspect your page, pause your code, watch variables and see every network request. In this topic you will learn a calm, step-by-step way to debug instead of guessing.

---

## 1. Opening DevTools

DevTools is available in Chrome, Edge, Firefox and Safari. The shortcuts are almost the same everywhere.

| Action | Windows / Linux | Mac |
| --- | --- | --- |
| Open DevTools | `F12` or `Ctrl + Shift + I` | `Cmd + Option + I` |
| Open the Console | `Ctrl + Shift + J` | `Cmd + Option + J` |
| Inspect an element | `Ctrl + Shift + C` | `Cmd + Shift + C` |

You can also right-click any element on a page and choose **Inspect**.

---

## 2. The Main Panels

| Panel | What it is used for |
| --- | --- |
| **Elements** | View and edit the live HTML and CSS |
| **Console** | Read messages and errors, run JavaScript |
| **Sources** | Read your code, set breakpoints, step through it |
| **Network** | See every request, its status, size and timing |
| **Application** | Inspect `localStorage`, `sessionStorage` and cookies |
| **Performance** | Find slow code and heavy rendering |

You will spend most of your time in the first four.

---

## 3. A Simple Debugging Process

Debugging is a method, not luck. Follow these steps every time.

* **Reproduce** the bug. Find the exact steps that make it happen.
* **Read** the error message and the line number it points to.
* **Isolate** the problem. Find the smallest piece of code that fails.
* **Inspect** the values. What are the variables really, not what you think they are?
* **Fix** one thing at a time.
* **Test** again to confirm the bug is gone and nothing else broke.

---

## 4. Reading Error Messages and Stack Traces

The Console shows errors in red. Each message tells you the **type**, a **description** and **where** it happened.

```javascript
function a() { b(); }
function b() { c(); }
function c() { throw new Error("Boom"); }

try {
  a();
} catch (error) {
  console.log(error.stack.split("\n")[0]);
}
```

```output
Error: Boom
```

The full `error.stack` lists the **call stack**: the chain of functions that led to the error, from the most recent call to the oldest.

* Read the first line for the message.
* Read the first file and line number to find where it happened.
* Read further down to see how your code got there.

---

## 5. Debugging with console Methods

`console.log` is the quickest debugging tool, and the console has many more methods.

| Method | Purpose |
| --- | --- |
| `console.log()` | General messages and values |
| `console.warn()` | Yellow warning |
| `console.error()` | Red error |
| `console.table()` | Show arrays and objects as a table |
| `console.group()` / `console.groupEnd()` | Indent related messages |
| `console.count(label)` | Count how many times a line runs |
| `console.assert(condition, message)` | Print a message only if the condition is `false` |
| `console.time(label)` / `console.timeEnd(label)` | Measure how long code takes |

```javascript
console.log("Name: %s, Age: %d", "Asha", 20);

console.count("click");
console.count("click");
console.count("click");

console.group("Order");
console.log("Item: Book");
console.log("Price: 499");
console.groupEnd();

console.assert(1 + 1 === 3, "Math is broken");
```

```output
Name: Asha, Age: 20
click: 1
click: 2
click: 3
Order
  Item: Book
  Price: 499
Assertion failed: Math is broken
```

> Log objects separately, for example `console.log({ total })`. Printing the variable inside an object shows its **name** and its value together.

## 6. Finding a Bug with console.log

This function should return the average, but it prints `NaN`.

```javascript
function average(numbers) {
  let total = 0;

  for (let i = 0; i <= numbers.length; i++) {
    total += numbers[i];
  }

  return total / numbers.length;
}

console.log(average([10, 20, 30]));
```

```output
NaN
```

Add a log inside the loop to see the real values.

```javascript
function average(numbers) {
  let total = 0;

  for (let i = 0; i <= numbers.length; i++) {
    console.log({ i, value: numbers[i], total });
    total += numbers[i];
  }

  return total / numbers.length;
}

average([10, 20, 30]);
```

```output
{ i: 0, value: 10, total: 0 }
{ i: 1, value: 20, total: 10 }
{ i: 2, value: 30, total: 30 }
{ i: 3, value: undefined, total: 60 }
```

On the last pass `value` is `undefined`, because index `3` does not exist. The loop uses `<=` instead of `<`. Here is the fix.

```javascript
function average(numbers) {
  let total = 0;

  for (let i = 0; i < numbers.length; i++) {
    total += numbers[i];
  }

  return total / numbers.length;
}

console.log(average([10, 20, 30]));
```

```output
20
```

## 7. Breakpoints in the Sources Panel

`console.log` changes your code. **Breakpoints** pause the running program so you can look around without editing anything.

To set a breakpoint:

* Open the **Sources** panel and choose your JavaScript file.
* Click a **line number**. A blue marker appears.
* Trigger the code (for example, click a button).
* The page freezes on that line, and you can inspect everything.

While paused, you can see:

* **Scope:** the current value of every variable.
* **Call Stack:** how the code reached this line.
* **Watch:** expressions you type in, re-evaluated at each step.

You can also hover over any variable in the code to see its value.

---

## 8. Stepping Through Code

Once paused, use the controls to move through the code one piece at a time.

| Control | Shortcut | What it does |
| --- | --- | --- |
| Resume | `F8` | Continue until the next breakpoint |
| Step over | `F10` | Run this line, skip into functions it calls |
| Step into | `F11` | Go inside the function being called |
| Step out | `Shift + F11` | Finish the current function and return to the caller |

A good routine is: pause just before the suspected problem, step **over** lines you trust and step **into** functions you do not.

---

## 9. The debugger Statement

Writing `debugger;` in your code works like a breakpoint, but it lives in the file. It pauses **only while DevTools is open**.

```javascript
function calculateTotal(price, quantity) {
  const subtotal = price * quantity;
  debugger;    // execution pauses here when DevTools is open
  const tax = subtotal * 0.18;
  return subtotal + tax;
}

console.log(calculateTotal(100, 2));
```

```output
236
```

Remove every `debugger` statement before publishing your site.

---

## 10. Advanced Breakpoints

Right-click a line number to reach more powerful breakpoint types.

* **Conditional breakpoint:** pauses only when an expression is true, for example `i === 3` or `user.id === 42`.
* **Logpoint:** prints a message to the Console without pausing and without editing code.
* **DOM breakpoint (Elements panel):** pauses when an element is changed or removed.
* **Event listener breakpoint (Sources panel):** pauses when an event such as `click` fires.
* **Pause on exceptions:** pauses at the exact line where an error is thrown.

Conditional breakpoints are a lifesaver inside loops that run hundreds of times.

---

## 11. Inspecting HTML and CSS in the Elements Panel

The Elements panel shows the **live DOM**, including changes made by JavaScript.

* Click an element to see its CSS rules in the **Styles** pane.
* Double-click text or a style value to edit it and see the result instantly.
* Edits are temporary and disappear when you refresh, which makes it a safe place to experiment.
* The **Computed** tab shows the final value of every CSS property.
* Select an element and type `$0` in the Console to access it from JavaScript.

---

## 12. Debugging Network Requests

When data does not load, open the **Network** panel **before** you trigger the request.

* **Status** tells you if the request worked (`200`), was not found (`404`) or crashed on the server (`500`).
* The **Headers** tab shows the URL, method and what you sent.
* The **Payload** tab shows the data you sent in a POST request.
* The **Response** and **Preview** tabs show exactly what the server returned.
* The **Timing** tab shows where the time was spent.
* Use the **Fetch/XHR** filter to hide images, styles and other noise.
* **Throttling** simulates a slow connection so you can test loading states.

Many "JavaScript bugs" are really network problems: a wrong URL, a missing header or a server error.

## 13. Debugging in the Browser

Press **Run**, then open DevTools (`F12`), go to the Console and click the button. Try setting a breakpoint inside `calculate` in the Sources panel.

```html
<!DOCTYPE html>
<html>
<body style="font-family: Arial, sans-serif; padding: 20px;">
  <input id="priceInput" type="number" value="250">
  <input id="qtyInput" type="number" value="3">
  <button id="calcBtn">Calculate</button>
  <p id="result">Total: -</p>

  <script>
    function calculate(price, quantity) {
      const subtotal = price * quantity;
      const tax = subtotal * 0.18;
      return subtotal + tax;
    }

    document.getElementById("calcBtn").addEventListener("click", () => {
      const price = document.getElementById("priceInput").value;
      const quantity = document.getElementById("qtyInput").value;

      console.log("Inputs:", { price, quantity });
      console.log("Types:", typeof price, typeof quantity);
      console.table([{ price, quantity }]);

      const total = calculate(Number(price), Number(quantity));
      document.getElementById("result").textContent = "Total: " + total.toFixed(2);
    });
  </script>
</body>
</html>
```

The logged types show that input values are **strings**. Without `Number(...)`, the result could be wrong.

## 14. Debugging Checklist for Common Bugs

| Symptom | What to check |
| --- | --- |
| `undefined` is not a function | Is the name spelled correctly? Is the script loaded before it is used? |
| `Cannot read properties of null` | Did `querySelector` find the element? Is the script placed after the HTML? |
| Nothing happens on click | Is the listener attached? Is the id or class correct? |
| Data does not appear | Check the Network panel, then `response.ok`, then the parsed data |
| Works once, then breaks | Is some state changed and never reset? |
| Wrong number or text | Check types with `typeof`; look for string vs number |

## Real-World Example

A shopping cart shows the wrong total. Instead of guessing, log the **inputs** and each **step** of the calculation:

```javascript
const cart = [
  { name: "Book", price: "499", qty: 2 },
  { name: "Pen", price: "20", qty: 5 }
];

function cartTotal(items) {
  let total = 0;

  items.forEach(item => {
    console.log(`${item.name}: price is a ${typeof item.price}`);
    total += item.price * item.qty;
  });

  return total;
}

console.log("Total:", cartTotal(cart));
```

```output
Book: price is a string
Pen: price is a string
Total: 1098
```

The result `1098` is correct here because `*` converts strings to numbers. But the log reveals that prices are strings, which would break `+` and comparisons elsewhere. Converting at the source with `Number(item.price)` prevents a whole family of bugs.

## Common Mistakes

### Guessing Instead of Inspecting

Changing code at random wastes time. Check the real values with a log or a breakpoint first.

### Ignoring the First Error

The first red error is usually the real cause. Later errors are often side effects of it.

### Leaving Debug Code in Production

```javascript
console.log("password:", password);    // never ship this
debugger;                              // pauses real users' browsers
```

Remove `debugger` and sensitive logs before publishing.

### Debugging an Old Cached Version

The browser may run an older copy of your file. Enable **Disable cache** in the Network panel while DevTools is open, or do a hard refresh.

### Changing Many Things at Once

Fix one problem, test, then move to the next. Otherwise you cannot tell which change helped.

### Opening the Network Panel Too Late

DevTools records requests only while it is open. Open it first, then reload or trigger the action.

### Forgetting That Edits in Elements Are Temporary

Changes made in DevTools disappear on refresh. Copy the working fix into your real files.

---

## Key Points

* DevTools opens with `F12`; the key panels are Elements, Console, Sources and Network.
* Debug with a method: reproduce, read, isolate, inspect, fix, test.
* The first line of an error says what went wrong; the stack trace shows how it got there.
* `console.log`, `table`, `group`, `count`, `assert` and `time` are useful debugging helpers.
* Breakpoints pause your code so you can inspect variables without editing files.
* Use Step over, Step into and Step out to move through code line by line.
* The `debugger` statement pauses code when DevTools is open; remove it before publishing.
* Conditional breakpoints and logpoints help inside loops.
* The Network panel shows status codes, payloads and responses for every request.
* Edits in the Elements panel are temporary, so experiment freely.
