# Chapter 10: Error Handling and Practical Projects

## Section 4: JavaScript Best Practices and Accessibility

Code that works is only the beginning. **Good** code is easy to read, safe to change, secure against misuse and usable by **everyone**, including people who use keyboards or screen readers. In this topic you will learn habits that professional developers follow, and how to make your interactive pages accessible.

---

## 1. Use Clear, Meaningful Names

Names are the first documentation. Choose names that explain **what** a value is or **what** a function does.

```javascript
// Hard to read
const d = 7;
function calc(a, b) { return a * b; }

// Easy to read
const daysInWeek = 7;
function calculateArea(width, height) { return width * height; }

console.log(calculateArea(4, daysInWeek));
```

```output
28
```

| Item | Convention | Example |
| --- | --- | --- |
| Variables and functions | `camelCase` | `userName`, `getTotal()` |
| Classes | `PascalCase` | `TaskManager` |
| Constants | `UPPER_SNAKE_CASE` | `MAX_ITEMS` |
| Booleans | Start with `is`, `has`, `can` | `isLoggedIn`, `hasError` |
| Functions | Start with a verb | `fetchUsers`, `renderList` |

---

## 2. Prefer const and let, Avoid var

* Use `const` by default.
* Use `let` only when the value must change.
* Avoid `var`, because it is function-scoped and hoisted in confusing ways.

```javascript
const taxRate = 0.18;
let total = 100;

total = total + total * taxRate;
console.log(total);
```

```output
118
```

---

## 3. Use Strict Equality

`===` compares value **and** type. `==` converts types first and can surprise you.

```javascript
console.log(0 == "");
console.log(0 === "");
console.log(null == undefined);
console.log(null === undefined);
console.log("5" == 5);
console.log("5" === 5);
```

```output
true
false
true
false
true
false
```

Always use `===` and `!==`.

## 4. Write Small Functions That Do One Thing

A function should be short and do one job. Small functions are easier to read, test and reuse.

```javascript
function isValidName(name) {
  return name.trim().length >= 2;
}

function formatName(name) {
  const clean = name.trim();
  return clean.charAt(0).toUpperCase() + clean.slice(1).toLowerCase();
}

function welcomeMessage(name) {
  if (!isValidName(name)) {
    return "Please enter a valid name";
  }
  return "Welcome, " + formatName(name) + "!";
}

console.log(welcomeMessage("  aSHA "));
console.log(welcomeMessage("a"));
```

```output
Welcome, Asha!
Please enter a valid name
```

## 5. Use Guard Clauses

Handle the bad cases **first** and return early. This avoids deep nesting.

```javascript
// Deeply nested
function discountNested(user) {
  if (user) {
    if (user.isMember) {
      if (user.orders > 5) {
        return 20;
      }
    }
  }
  return 0;
}

// Guard clauses: flat and clear
function discount(user) {
  if (!user) return 0;
  if (!user.isMember) return 0;
  if (user.orders <= 5) return 0;

  return 20;
}

console.log(discount({ isMember: true, orders: 8 }));
console.log(discount(null));
```

```output
20
0
```

## 6. Avoid Magic Numbers

A **magic number** is a value with no explanation. Give it a name.

```javascript
// Unclear
function price(total) {
  return total + total * 0.18;
}

// Clear
const GST_RATE = 0.18;
const MAX_TITLE_LENGTH = 50;

function priceWithTax(total) {
  return total + total * GST_RATE;
}

console.log(priceWithTax(200));
console.log(MAX_TITLE_LENGTH);
```

```output
236
50
```

If the tax rate changes, you edit one line instead of hunting through the whole file.

## 7. Do Not Repeat Yourself (DRY)

If you copy the same code in several places, put it in one function.

```javascript
// Repeated
console.log("Total: ₹" + (499 * 2).toFixed(2));
console.log("Total: ₹" + (20 * 5).toFixed(2));

// Reusable
function formatPrice(amount) {
  return "₹" + amount.toFixed(2);
}

console.log("Total: " + formatPrice(499 * 2));
console.log("Total: " + formatPrice(20 * 5));
```

```output
Total: ₹998.00
Total: ₹100.00
Total: ₹998.00
Total: ₹100.00
```

## 8. Write Useful Comments

Good code explains **what** it does through names. Comments should explain **why**.

```javascript
// Bad: repeats the code
// add 1 to count
let count = 0;
count = count + 1;

// Good: explains the reason
// The API counts pages from 1, but our array index starts at 0
const pageIndex = 3 - 1;

console.log(count, pageIndex);
```

```output
1 2
```

Delete old commented-out code. Version control remembers it for you.

---

## 9. Avoid Global Variables and Mutating Inputs

Globals can be changed from anywhere, which makes bugs hard to trace. Keep data inside functions or modules, and avoid changing the arguments you receive.

```javascript
const original = [3, 1, 2];

// Mutates the original array
function sortBad(items) {
  return items.sort();
}

// Works on a copy
function sortGood(items) {
  return [...items].sort();
}

console.log(sortGood(original));
console.log(original);
```

```output
[ 1, 2, 3 ]
[ 3, 1, 2 ]
```

## 10. Handle Errors and Edge Cases

Assume that input can be empty, wrong or missing. Check it before using it.

```javascript
function getFirstLetter(text) {
  if (typeof text !== "string" || text.trim() === "") {
    return "";
  }
  return text.trim()[0].toUpperCase();
}

console.log("[" + getFirstLetter("codify") + "]");
console.log("[" + getFirstLetter("") + "]");
console.log("[" + getFirstLetter(null) + "]");
```

```output
[C]
[]
[]
```

Optional chaining (`?.`) and the nullish operator (`??`) make safe access short.

```javascript
const user = { profile: { name: "Asha" } };

console.log(user.profile?.name);
console.log(user.address?.city);
console.log(user.address?.city ?? "Unknown city");
```

```output
Asha
undefined
Unknown city
```

## 11. Security Basics

Anything a user types or a server sends is **untrusted**.

* Use `textContent` to display user text. Avoid `innerHTML` with untrusted data.
* Never use `eval()` or `new Function()` on user input.
* Validate input in JavaScript for convenience, and **again on the server** for safety.
* Never store passwords or secret keys in front-end code or `localStorage`.

```html
<!DOCTYPE html>
<html>
<body style="font-family: Arial, sans-serif; padding: 20px;">
  <input id="textInput" value="<b>Hello</b>">
  <button id="showBtn">Show</button>
  <p>Using textContent: <span id="safe"></span></p>

  <script>
    document.getElementById("showBtn").addEventListener("click", () => {
      const value = document.getElementById("textInput").value;
      document.getElementById("safe").textContent = value;
    });
  </script>
</body>
</html>
```

The tags appear as plain text instead of being treated as HTML.

## 12. Performance Habits

* Avoid touching the DOM inside big loops. Build the content first, then insert once.
* Use **event delegation** (Chapter 8) instead of many listeners.
* Use `debounce` for events that fire rapidly, such as typing or resizing.
* Load heavy code only when needed with dynamic `import()`.

A **debounce** waits until the user stops before running the function.

```javascript
function debounce(callback, delay) {
  let timerId;
  return function (...args) {
    clearTimeout(timerId);
    timerId = setTimeout(() => callback(...args), delay);
  };
}

const search = debounce(text => console.log("Searching for: " + text), 300);

search("j");
search("ja");
search("jav");
search("java");
```

```output
Searching for: java
```

Four quick calls produced only one real search.

## 13. What Is Accessibility?

**Accessibility** (often written **a11y**) means building pages that everyone can use, including people who:

* Use only a **keyboard**.
* Use a **screen reader** that reads the page aloud.
* Have **low vision** or **color blindness**.
* Have **motor** difficulties and cannot use a mouse precisely.
* Are in bright sunlight or on a slow connection.

Accessible pages are also better for search engines, easier to test and nicer for everyone.

## 14. Use the Right HTML Element

Native elements give you keyboard support, focus and screen reader meaning for free.

```html
<!-- Bad: a div pretending to be a button -->
<div class="btn" onclick="save()">Save</div>

<!-- Good: a real button -->
<button type="button" id="saveBtn">Save</button>
```

* A `<button>` can be focused with `Tab` and activated with `Enter` and `Space`.
* A `<div>` can do none of that without extra work.
* Use `<button>` for actions, `<a href>` for navigation, `<label>` for form fields.

---

## 15. Keyboard Access and Focus

Everything you can do with a mouse must be possible with a keyboard.

* Do not remove focus outlines without a replacement style.
* When content appears (a dialog, an error), **move focus** to it or announce it.
* After deleting an item, send focus somewhere sensible, for example the input field.
* Never trap the keyboard inside an element without a way out (usually `Escape`).

```css
button:focus-visible,
input:focus-visible {
  outline: 3px solid #0077ff;
  outline-offset: 2px;
}
```

---

## 16. ARIA Attributes

**ARIA** attributes add extra meaning when plain HTML is not enough. Use them to **support** native elements, never to replace them.

| Attribute | Purpose |
| --- | --- |
| `aria-label` | Gives an element an accessible name (useful for icon buttons) |
| `aria-expanded` | Tells whether a collapsible section is open (`true` or `false`) |
| `aria-controls` | Links a button to the element it controls |
| `aria-pressed` | Shows the state of a toggle button |
| `aria-live` | Announces changed content to screen readers |
| `aria-invalid` | Marks a form field with an error |
| `role="alert"` | Announces an urgent message immediately |

---

## 17. An Accessible Toggle Section

Press **Run**. Try using only the `Tab` and `Enter` keys. A screen reader announces whether the section is expanded or collapsed.

```html
<!DOCTYPE html>
<html>
<head>
  <style>
    body { font-family: Arial, sans-serif; padding: 20px; }
    button { padding: 8px 14px; font-size: 1rem; cursor: pointer; }
    button:focus-visible { outline: 3px solid #0077ff; outline-offset: 2px; }
    #details { margin-top: 10px; padding: 10px; background: #eef4ff; }
    #details[hidden] { display: none; }
  </style>
</head>
<body>
  <button type="button" id="toggleBtn" aria-expanded="false" aria-controls="details">
    Show details
  </button>

  <div id="details" hidden>
    This section is announced correctly by screen readers.
  </div>

  <script>
    const button = document.getElementById("toggleBtn");
    const details = document.getElementById("details");

    button.addEventListener("click", () => {
      const isOpen = button.getAttribute("aria-expanded") === "true";

      button.setAttribute("aria-expanded", String(!isOpen));
      details.hidden = isOpen;
      button.textContent = isOpen ? "Show details" : "Hide details";
    });
  </script>
</body>
</html>
```

## 18. Announcing Changes with aria-live

When JavaScript updates the page, a screen reader user does not see it. An **aria-live** region speaks the new text automatically.

```html
<!DOCTYPE html>
<html>
<body style="font-family: Arial, sans-serif; padding: 20px;">
  <button type="button" id="addBtn">Add to cart</button>
  <p>Items in cart: <span id="count">0</span></p>

  <p id="status" role="status" aria-live="polite" style="color: #0a7a2f;"></p>

  <script>
    let items = 0;

    document.getElementById("addBtn").addEventListener("click", () => {
      items++;
      document.getElementById("count").textContent = items;
      document.getElementById("status").textContent = "Item added. Cart has " + items + " items.";
    });
  </script>
</body>
</html>
```

* Use `aria-live="polite"` for normal updates.
* Use `role="alert"` for urgent errors.
* Place the live region in the HTML **before** its text changes.

## 19. Accessible Forms

* Connect each input to a `<label>` using `for` and `id`.
* Do not use the placeholder as the only label.
* Show errors in text, not only in red.
* Mark invalid fields with `aria-invalid="true"` and link the message with `aria-describedby`.

```html
<label for="email">Email address</label>
<input id="email" type="email" aria-describedby="emailError" aria-invalid="false">
<p id="emailError" role="alert"></p>
```

---

## 20. Other Accessibility Checks

* Give every meaningful image an `alt` description; use `alt=""` for decorations.
* Keep enough **color contrast** between text and background.
* Do not use color as the **only** way to show meaning (add text or an icon).
* Respect users who prefer less motion.
* Make click targets large enough for fingers.
* Test your page using **only the keyboard**.

```css
@media (prefers-reduced-motion: reduce) {
  * {
    animation: none !important;
    transition: none !important;
  }
}
```

## Real-World Example

A reusable form checker that follows the best practices from this topic: clear names, a constant, guard clauses and one job per function:

```javascript
const MIN_PASSWORD_LENGTH = 8;

function validatePassword(password) {
  if (typeof password !== "string") return "Password is required";
  if (password.length < MIN_PASSWORD_LENGTH) {
    return `Use at least ${MIN_PASSWORD_LENGTH} characters`;
  }
  if (!/\d/.test(password)) return "Include at least one number";

  return "";
}

function describeResult(password) {
  const error = validatePassword(password);
  return error === "" ? "Password accepted" : error;
}

console.log(describeResult("abc"));
console.log(describeResult("abcdefgh"));
console.log(describeResult("abcdefg1"));
```

```output
Use at least 8 characters
Include at least one number
Password accepted
```

The returned message can then be shown in an element with `role="alert"` so that everyone is told about the problem.

## Common Mistakes

### Using Vague Names

```javascript
const x = getData();     // what is x?
const users = getUsers(); // clear
```

### Using == Instead of ===

```javascript
if (value == 0) { }     // also true for "" and false
if (value === 0) { }    // correct
```

### Making a div Clickable Instead of Using a Button

Divs are not focusable and have no keyboard support. Use `<button>`.

### Removing the Focus Outline

```css
* { outline: none; }    /* keyboard users can no longer see where they are */
```

Style `:focus-visible` instead of removing it.

### Using innerHTML with User Input

```javascript
output.innerHTML = userText;      // can run harmful HTML
output.textContent = userText;    // safe
```

### Relying on Color Alone

A red border by itself is invisible to color-blind users. Add an error message in text.

### Using a Placeholder as a Label

Placeholders disappear when typing and are not reliable labels. Use a real `<label>`.

### Updating the Page Silently

Screen reader users never learn that something changed. Use an `aria-live` region or `role="alert"`.

### Ignoring Edge Cases

Test with empty input, very long input, wrong types and rapid repeated clicks.

## Key Points

* Use clear names: `camelCase` for variables and functions, `PascalCase` for classes.
* Prefer `const` and `let`; avoid `var`.
* Use `===` and `!==` instead of `==` and `!=`.
* Keep functions small, use guard clauses and replace magic numbers with named constants.
* Do not repeat code; do not rely on globals; do not mutate input arguments.
* Comments should explain **why**, not repeat **what**.
* Treat all input as untrusted: use `textContent`, never `eval`, validate on the server too.
* Debounce rapid events and avoid heavy DOM work inside loops.
* Accessibility means everyone can use your page, including keyboard and screen reader users.
* Use native elements (`button`, `a`, `label`) before reaching for ARIA.
* Keep visible focus, manage focus after changes and announce updates with `aria-live`.
* Never use color alone to carry meaning; keep good contrast and text labels.
