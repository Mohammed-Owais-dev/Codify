# Chapter 9: Asynchronous JavaScript

## Section 1: Synchronous vs Asynchronous Code

JavaScript can do only one thing at a time, yet web pages load data, run timers and respond to clicks without freezing. The secret is **asynchronous** code. In this topic you will learn how synchronous and asynchronous code differ, why blocking the page is bad, and how the event loop keeps everything running smoothly.

---

## 1. Synchronous Code

**Synchronous** code runs line by line, in order. Each line must finish before the next one starts.

```javascript
console.log("Wake up");
console.log("Brush teeth");
console.log("Have breakfast");
```

```output
Wake up
Brush teeth
Have breakfast
```

* JavaScript reads the code from top to bottom.
* Each statement waits for the previous one to complete.
* This is easy to predict, but it becomes a problem when one step takes a long time.

---

## 2. The Blocking Problem

JavaScript runs on a **single thread**. If one task takes a long time, everything else must wait. This is called **blocking**.

```javascript
function blockFor(ms) {
  const end = Date.now() + ms;
  while (Date.now() < end) {
    // do nothing, just keep the thread busy
  }
}

console.log("Start");
blockFor(2000);
console.log("Finished blocking");
console.log("End");
```

```output
Start
Finished blocking
End
```

The output looks normal, but the program was frozen for two seconds. In a browser, a blocked thread means:

* Buttons do not respond to clicks.
* Animations stop.
* Scrolling becomes stuck.
* The browser may show a "page not responding" warning.

---

## 3. Asynchronous Code

**Asynchronous** code starts a long task and **moves on** without waiting. When the task finishes, JavaScript comes back to handle the result.

```javascript
console.log("Start");

setTimeout(() => {
  console.log("Timer finished");
}, 1000);

console.log("End");
```

```output
Start
End
Timer finished
```

* `setTimeout` starts a timer and returns immediately.
* JavaScript continues with `End` instead of waiting.
* After one second, the callback runs and prints `Timer finished`.

Even with a delay of `0`, the callback still runs **after** the current synchronous code finishes.

```javascript
console.log("A");

setTimeout(() => console.log("B"), 0);

console.log("C");
```

```output
A
C
B
```

---

## 4. The Event Loop

How can a single-threaded language handle async work? It gets help from the browser (or Node.js) and a mechanism called the **event loop**.

```text
          +-----------------+
          |   Call Stack    |   runs your code, one task at a time
          +-----------------+
                  ^
                  |  moves a callback in when the stack is empty
          +-----------------+
          |   Event Loop    |   keeps checking the queues
          +-----------------+
             ^            ^
             |            |
   +----------------+  +-------------------+
   | Microtask Queue|  |  Callback Queue   |
   | (Promises)     |  | (timers, events)  |
   +----------------+  +-------------------+
             ^            ^
             |            |
        +---------------------------+
        |  Web APIs (browser/Node)  |   timers, fetch, DOM events
        +---------------------------+
```

How it works, step by step:

* **Call Stack** runs your synchronous code.
* **Web APIs** handle slow work (timers, network requests, clicks) outside the stack.
* When the work finishes, its callback goes into a **queue**.
* The **event loop** moves a callback onto the stack only when the stack is **empty**.
* **Microtasks** (Promise callbacks) always run before the next timer or event callback.

---

## 5. Microtasks vs Timer Callbacks

Promise callbacks have higher priority than `setTimeout` callbacks, even when the timer delay is `0`.

```javascript
console.log("1: sync");

setTimeout(() => console.log("4: timeout"), 0);

Promise.resolve().then(() => console.log("3: promise"));

console.log("2: sync");
```

```output
1: sync
2: sync
3: promise
4: timeout
```

The order is always:

* All **synchronous** code first.
* Then all **microtasks** (Promises).
* Then the next **timer or event** callback.

---

## 6. Common Asynchronous Operations

Many everyday tasks are asynchronous because they depend on something outside JavaScript.

| Operation | Example | Why it is async |
| --- | --- | --- |
| Timers | `setTimeout`, `setInterval` | Wait for time to pass |
| Network requests | `fetch("/api/users")` | Server needs time to reply |
| User events | `click`, `keydown` | Nobody knows when the user acts |
| Files (Node.js) | `fs.readFile` | Disk is slower than memory |
| Animations | `requestAnimationFrame` | Wait for the next screen repaint |

## 7. Async in the Browser

Press **Run**. While the data is "loading", the second button still responds, because the timer does not block the page.

```html
<!DOCTYPE html>
<html>
<body style="font-family: Arial, sans-serif; padding: 20px;">
  <button id="loadBtn">Load Data</button>
  <button id="countBtn">Clicked 0 times</button>
  <p id="status">Waiting...</p>

  <script>
    let clicks = 0;

    document.getElementById("loadBtn").addEventListener("click", () => {
      const status = document.getElementById("status");
      status.textContent = "Loading...";

      setTimeout(() => {
        status.textContent = "Data loaded!";
      }, 2000);
    });

    document.getElementById("countBtn").addEventListener("click", (event) => {
      clicks++;
      event.target.textContent = "Clicked " + clicks + " times";
    });
  </script>
</body>
</html>
```

Click **Load Data**, then keep clicking the counter button. The page stays responsive for the whole two seconds.

## 8. Three Ways to Write Async Code

JavaScript has three styles for working with asynchronous results. You will learn each one in this chapter.

```javascript
const wait = ms => new Promise(resolve => setTimeout(resolve, ms));

// 1. Callbacks
setTimeout(() => console.log("Callback style done"), 100);

// 2. Promises
wait(200).then(() => console.log("Promise style done"));

// 3. async / await
async function run() {
  await wait(300);
  console.log("async/await style done");
}
run();
```

```output
Callback style done
Promise style done
async/await style done
```

* **Callbacks** are the oldest style and can become deeply nested.
* **Promises** (Topic 9.3) give a cleaner way to chain steps.
* **async / await** (Topic 9.4) makes async code look like normal code.

## Real-World Example

A food delivery app places your order and keeps the screen usable while the restaurant works:

```javascript
console.log("Order placed");

setTimeout(() => {
  console.log("Restaurant is preparing your food");
}, 500);

setTimeout(() => {
  console.log("Delivery partner is on the way");
}, 1000);

console.log("You can keep browsing the app");
```

```output
Order placed
You can keep browsing the app
Restaurant is preparing your food
Delivery partner is on the way
```

The app never freezes. It starts the slow steps, continues running, and reacts when each step finishes.

## Common Mistakes

### Expecting Async Code to Run in Order

```javascript
setTimeout(() => console.log("First?"), 1000);
console.log("Second?");    // prints before the timer callback
```

### Using the Result Before It Is Ready

```javascript
let data;
setTimeout(() => { data = "loaded"; }, 500);
console.log(data);    // undefined, because the callback has not run yet
```

Use the value **inside** the callback, a `.then()`, or after `await`.

### Blocking the Thread with Long Loops

```javascript
while (true) {
  // freezes the whole page, nothing else can run
}
```

Break big work into smaller pieces or use asynchronous APIs.

### Thinking setTimeout with 0 Runs Immediately

```javascript
setTimeout(() => console.log("Not immediate"), 0);
console.log("Runs first");
```

A zero delay only means "run as soon as the stack is empty".

### Confusing Asynchronous with Multithreaded

JavaScript still runs your code on one thread. Async work is done by the browser or Node.js, and only the callbacks come back to your thread.

---

## Key Points

* Synchronous code runs line by line; each line waits for the previous one.
* Long synchronous tasks **block** the single JavaScript thread and freeze the page.
* Asynchronous code starts a task and continues; the result is handled later.
* The **event loop** moves callbacks to the call stack only when the stack is empty.
* Promise callbacks (microtasks) run before timer callbacks.
* Timers, network requests and user events are all asynchronous.
* Callbacks, Promises and `async/await` are three ways to handle async results.
* Never use a value before the async task that produces it has finished.
